# Incident Report 003: Temporary Local Administrator Account

**Status:** Closed — authorized lab simulation
**Analyst:** Shams
**Date of activity:** 2026-07-23
**Severity:** High (Wazuh level 12 on the group change)

---

## Executive Summary

On 2026-07-23 at 07:50:11 UTC, a local account named `soc_lab_temp_admin` was
created on `WIN11-SOC-ENDPOINT`, added to the local `Administrators` group,
removed from that group, and deleted — the entire sequence completing in
**100 milliseconds**.

The activity was generated by
`Invoke-SocLabScenario.ps1 -Scenario TemporaryAdmin`. Every step was captured
by Windows Security auditing and forwarded to Wazuh, producing seven alerts
across four Wazuh rules.

This case is the most instructive of the three, for two reasons. First, no
single alert describes what actually happened; the meaning lives in the
*sequence*. Second, investigating it exposed an incorrect MITRE mapping in
Wazuh's built-in ruleset, which the triage policy now corrects.

## Investigation

### The SID resolution problem

The `4732` event — the privilege escalation, and the highest-severity alert in
the set — does **not** name the account that was added. Its `eventdata`
contains:

```text
subjectUserName: Shams
targetUserName:  Administrators        (the group, not the member)
memberName:      (empty)
memberSid:       S-1-5-21-3627987222-3469180906-1209694690-1003
```

An analyst looking at this alert alone knows *someone* was granted local admin,
but not who. Identifying the member requires correlating the SID's RID (`1003`)
back to the `4720` creation event 31 ms earlier.

This is why [`server.py`](../../soc-ai-platform/server.py) extracts `memberSid`
and `memberName` into a dedicated `account` block during normalization — the
correlation field has to survive into the console, or the analyst is stuck
pivoting in raw JSON.

### Why the sequence matters more than any single alert

Read individually, each alert is unremarkable on a workstation:

- An account was created. Could be provisioning.
- An account was added to Administrators. Could be a helpdesk grant.
- An account was deleted. Could be cleanup.

Read as a sequence within 100 ms, it is a recognisable attacker pattern:
establish a privileged foothold, use it, and remove the evidence. The deletion
is the part that should worry an analyst most — it is anti-forensic behaviour,
and it means the account no longer exists to be examined.

**Detection gap identified.** Wazuh alerts on each step independently. Nothing
in the current pipeline says "the same actor created, elevated, and deleted an
account inside two seconds." That correlation is left to the analyst. Closing it
properly would need either a Wazuh composite rule or a correlation layer above
the alert stream.

### Simulation fidelity limits

The 100 ms lifecycle is an artifact of the script, which creates and reverts in
a single `try/finally`. A real attacker would keep the account for days or
weeks. The detections written here trigger on the individual behaviours, so
they are unaffected by the compressed timing — but any *correlation* rule built
from this data must not assume a sub-second window, or it will miss the real
version of this attack.

## MITRE ATT&CK Mapping

| Technique | Tactic | Evidence | Confidence |
| --- | --- | --- | --- |
| `T1136.001` — Create Account: Local Account | Persistence | Event `4720`, account `soc_lab_temp_admin` | High |
| `T1098` — Account Manipulation | Persistence, Privilege Escalation | Event `4732`, added to local `Administrators` | High |
| `T1070` — Indicator Removal | Defense Evasion | Events `4733` and `4726`, group membership and account removed | Medium |

### Correction to Wazuh's built-in mapping

Wazuh rule `60154` ("Administrators Group Changed") ships with this mapping:

```json
"mitre": {
  "id":        ["T1484"],
  "technique": ["Domain Policy Modification"],
  "tactic":    ["Defense Evasion", "Privilege Escalation"]
}
```

**This is incorrect for the observed event.** `T1484` covers modification of
domain-level policy objects — Group Policy Objects, domain trusts. Event `4732`
here is a change to a *local* security group on a standalone workstation. The
event data confirms both points:

```text
subjectDomainName: WIN11-SOC-ENDPO   (the machine's own NetBIOS name, not an AD domain)
targetDomainName:  Builtin           (a local group namespace)
```

A domain-joined host would carry the Active Directory domain name in
`subjectDomainName`. The local `Administrators` group is not a domain policy
object, so `T1484` does not apply.

The accurate mapping is `T1098` (Account Manipulation), which is what triage
policy `SOC-ACCOUNT-002` asserts. The console displays both the Wazuh mapping
and the policy mapping so the discrepancy is visible rather than silently
overwritten.

**Takeaway:** vendor ATT&CK mappings are a starting point, not ground truth. An
analyst who copies `T1484` into a report because Wazuh said so has published a
factual error about what the adversary did.

## Detection Logic

Sigma rules:

- [`Detections/sigma/local_admin_account_created.yml`](../../Detections/sigma/local_admin_account_created.yml) — event `4720`
- [`Detections/sigma/member_added_to_local_admins.yml`](../../Detections/sigma/member_added_to_local_admins.yml) — event `4732`, scoped to privileged groups

Wazuh hunting query for the whole lifecycle:

```text
data.win.system.channel: "Security" and data.win.system.eventID: (4720 or 4722 or 4726 or 4732 or 4733 or 4738)
```

Triage policy rules added as a result of this investigation:

| Rule | Event | Score | MITRE |
| --- | --- | ---: | --- |
| `SOC-ACCOUNT-001` | `4720` created | 92 | T1136.001 |
| `SOC-ACCOUNT-002` | `4732` added to admins | 96 | T1098 |
| `SOC-ACCOUNT-004` | `4733` removed from admins | 90 | T1098, T1070 |
| `SOC-ACCOUNT-005` | `4726` deleted | 88 | T1070 |
| `SOC-ACCOUNT-006` | `4722` / `4738` enabled or changed | 85 | T1098 |

`SOC-ACCOUNT-004` through `006` did not exist before this investigation. Events
`4722`, `4726`, `4733`, and `4738` previously matched only the lab-marker rule,
so they were labelled "SOC lab administrator scenario" instead of describing the
behaviour. That is now fixed.

**False positives.** Helpdesk workflows grant temporary local admin rights
legitimately, and endpoint management platforms adjust group membership
routinely. The discriminator is the *pattern*: an approved grant is not
normally followed by deletion of the account minutes later.

## Response Actions Taken

Authorized lab activity; no containment required. The account was removed by the
simulation script itself and verified absent.

Production response would be:

1. **Do now:** resolve the `memberSid` to an account name and determine whether
   that account still exists.
2. **Do now:** identify the actor in `subjectUserName` and confirm whether they
   had authorization to create accounts.
3. **Do if confirmed:** disable the actor's account, isolate the endpoint, and
   preserve Security logs before rotation — the deleted account exists only in
   logs now.
4. **Follow up:** hunt for `4720` followed by `4732` across all endpoints, and
   review whether local admin grants have an approval trail.

## Lessons Learned

1. **The highest-severity alert was the least self-explanatory.** The level 12
   `4732` names a group but not a member. Severity and investigability are not
   the same thing.
2. **Vendor MITRE mappings need review.** Wazuh's `T1484` for a local group
   change would have put a wrong technique in a published report.
3. **Per-event alerting misses sequence-based attacks.** Seven correct alerts
   still did not say what happened. This is the strongest argument in the lab so
   far for a correlation layer.
4. **Triage coverage gaps are invisible until you look.** Four of the seven
   events fell through to a lab-marker rule. Nothing was broken — the labels
   were just wrong, which is worse, because it looks like it works.
